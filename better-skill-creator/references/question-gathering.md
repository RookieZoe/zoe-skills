# 反问收集

当用户给出的创建描述过于简单时，不要直接脑补完整 skill。先用最少量问题，把会影响立项、边界和产出的关键信息补齐。

## 什么时候触发

- 用户只给了一句抽象需求，例如“帮我做个写作 skill”“做一个 review skill”。
- 现有信息不足以判断它是否真的值得做成 skill。
- 现有信息不足以确定主任务边界、触发条件、不适用场景或最终产出。
- 用户希望直接生成完整 skill，但没有给任何现成素材、示例输入输出或环境前提。

## 提问原则

- 只问当前决策真正需要的问题；能从用户原话、现有文件或已有 skill 推断出来的，不重复问。
- 默认先问 2 到 3 个最关键问题；只有前一轮回答后仍不足以落地，才继续追加。
- 优先补齐“主任务 / 触发示例 / 反例 / 产出 / 现有素材”。
- 问题要短、具体、可直接回答，不要做开放式采访。
- 如果涉及付费 API、外部写操作、上传、删除、部署等副作用，单独补问确认条件。

## 优先问题

1. 这个 skill 最核心只做哪一件事？请用一句话描述，最好是“动词 + 对象 + 产出”。
2. 你希望它在什么请求下被触发？给我 2 到 3 个典型用户输入例子。
3. 哪些需求看起来相近，但其实不该交给它？给我 2 到 4 个反例。
4. 这个 skill 最终要产出什么？是判断建议、`SKILL.md`、模板、脚本，还是完整 skill 目录？
5. 你现在已经有什么现成素材？比如 prompt、SOP、脚本、模板、示例输入输出、参考文档。
6. 这个 skill 依赖什么宿主或运行环境？有没有平台格式、工具限制、目录约定之类的前提？
7. 它会不会调用外部 API、写外部系统、上传、删除、部署之类的高风险动作？如果会，确认条件是什么？

## 最小三问

如果用户输入非常模糊，优先从下面三问开始，而不是一次性发完整问卷。

1. 这个 skill 最核心只做哪一件事？请用一句话描述。
2. 你希望它在什么请求下被触发，又有哪些相邻需求不该交给它？各给我几个例子。
3. 它最终要产出什么，你手头已经有什么现成素材？

## 什么时候停止追问

- 已经能判断它应不应该做成 skill。
- 已经能确定单一主任务和主设计模式。
- 已经能写出 `description`，以及“适用 / 不适用 / 产出 / 反例”。
- 已经能判断是否需要 `references/`、`assets/`、`scripts/`，以及是否存在高风险副作用。
- 剩余空白不会影响 skill 的结构和路由时，停止追问，直接继续创建或更新。

## 收集后的整理

- 用 4 到 6 行把已知信息收束成：主任务、触发示例、反例、产出、现有素材、风险前提。
- 如果用户回答显示它其实不该做成 skill，回到立项判断，明确给出替代方案。
- 如果用户回答暴露出两个独立主任务，先拆边界，再决定是否拆成两个 skill。
