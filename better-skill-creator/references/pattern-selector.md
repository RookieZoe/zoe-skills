# 模式选择

为 Skill 选择一个主设计模式。先定主模式，再决定是否需要少量次级模式来补强某个步骤。

| 模式 | 适合什么任务 | 典型 supporting files | 不适合什么任务 |
| --- | --- | --- | --- |
| `tool-wrapper` | 把某个框架、工具、接口约定封装成按需上下文 | `references/`、`scripts/` | 需要固定多步门控或模板输出的任务 |
| `generator` | 基于模板稳定产出文档、方案、报告、配置 | `assets/`、`references/` | 只做审查或只做工具约束 |
| `reviewer` | 根据清单、严重级别或标准做审查 | `references/review-checklist.md` | 以生成内容为主的任务 |
| `inversion` | 必须先访谈用户、补齐条件后再继续 | 提问顺序说明、模板 | 单轮就能直接执行的任务 |
| `pipeline` | 明确多步骤、必须按顺序推进、不能跳步 | `references/`、`assets/`、检查清单 | 只是应用一套约定或单步生成的任务 |

## 选择规则

- 如果先应用规则或框架约定再行动，优先 `tool-wrapper`。
- 如果最终必须产出固定骨架的文档或配置，优先 `generator`。
- 如果重点是按清单审查、找问题、给严重级别，优先 `reviewer`。
- 如果没有补齐上下文就不能安全继续，优先 `inversion`。
- 如果任务天然分成严格顺序的多步，并且每步都有门控，优先 `pipeline`。

## 快速决策

- 先问自己：这是在“应用约定”“生成产物”“做审查”“先访谈”“跑流程”中的哪一种主任务。
- 如果答案明显只有一种，就直接选它作为主模式。
- 如果答案看起来像两种，先找出哪一种决定了 Skill 的对外路由和成功标准，那一个就是主模式。
- 只有当另一个模式只是补强某一步，而不是改变整个 Skill 的主要职责时，才把它作为次级模式保留。

## 混合规则

- 设计模式不是互斥的；可以组合，但元数据里仍然只写一个主模式。
- 组合模式时，要先说明主模式，再说明次级模式只服务于哪个步骤。
- 常见组合：
  - `pipeline` 在最后一步挂一个 `reviewer` 检查。
  - `generator` 在开头先用 `inversion` 访谈补变量。
  - `tool-wrapper` 在执行步骤里嵌入 `reviewer` 清单做自检。
- 如果次级模式已经扩展到整个 Skill 的大部分步骤，通常说明主模式选错了，或应该拆 skill。
- 次级模式所需的说明、模板、检查清单只应在对应步骤按需加载，不要提前全部常驻。
- 如果一个 skill 同时强覆盖 review、generate、deploy、debug，通常不是混合，而是边界失控。
- 优先拆成多个原子 skill，再让上层 Agent 或 Workflow 负责编排。

## 设计提醒

- Skill 不是 Prompt、Workflow、Agent 的替代，而是能力封装层。
- 一个 Skill 可以内部调用脚本、模板、检索或工作流，但对外仍然只暴露一个主任务。
