# 复核清单

完成创建或重构后，逐项检查。

## 立项

- 这个需求真的值得做成 Skill，而不是普通文档或一次性 Prompt。
- Skill 的主任务足够单一，不是在打包一堆无关任务。

## 路由

- YAML 头部存在且合法。
- `name` 与目录名一致，且符合 slug 规则。
- `description` 是一行，且包含“适用 / 不适用 / 产出”。
- `description` 没有 XML 尖括号，也没有混入实现细节。
- `SKILL.md` 中有清晰的“适用 / 不适用 / 产出 / 反例”。
- 反例能覆盖最容易误触发的相邻需求。

## 模式

- 五种设计模式里已经选定一个主模式。
- 正文流程和主模式是一致的，而不是名义上选一种，实际上又写成另一种。
- 如果用了组合模式，主模式仍然一眼可见，次级模式只服务于局部步骤。
- 次级模式没有把 Skill 的边界扩张成另一个独立任务。

## 结构

- `SKILL.md` 足够精简，没有把完整工作手册塞进去。
- 详细规则已拆进 `references/`。
- 模板只在需要时放进 `assets/`。
- 代码只在需要时放进 `scripts/`。
- 如果用了组合模式，相关 `references/` 或 `assets/` 只在对应步骤被读取，没有一次性前置加载。

## 可移植性

- 核心 Skill 只依赖 `SKILL.md` 与必要的 supporting files 就能成立。
- 没有把某个平台的 companion 文件误当成通用必备结构。
- 如果用户未指定宿主产品，就没有提前写入平台专属配置。

## 质量

- Skill 沉淀的是可复用 SOP，不是人格模仿。
- 约束和输出格式足够明确，不只是在写角色设定。
- supporting files 不重复、不空转、不为“看起来完整”而堆文件。
